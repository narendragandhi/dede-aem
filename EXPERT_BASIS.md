# Architectural Basis & Expert Justification for Dede-Java

This document defines the technical pillars of `dede-java`. Its primary objective is **Architectural Impact Analysis**: understanding the complex, multi-layered relationships between Dispatcher configurations, JCR content structures, and OSGi service dynamics.

### The Unified Theory of Impact
To avoid "feature creep," every capability of `dede-java` is filtered through the lens of **Relationship Intelligence**:
1.  **Vertical Impact:** Reachability from the Web (Dispatcher) to the Code (Servlet/Service).
2.  **Horizontal Impact:** Coupling between the Content (JCR) and the Logic (Sling Models).
3.  **Temporal Impact:** Compatibility across Lifecycle changes (SDK updates, Cloud migrations).

---

## 1. The "Unified Dependency Graph" (The North Star)
In a standard AEM project, dependencies are fragmented across three disconnected silos:
1.  **Code (Java/OSGi):** Managed by Maven and analyzed by IDEs.
2.  **Configuration (Dispatcher):** Static `.any` or `.vhost` files.
3.  **Content (JCR/Sling):** XML/Protobuf structures defining resource types and component hierarchies.

**The Dede-Java Value:** It builds a **Digital Twin** that links these silos. It traces a request from a **Dispatcher Filter** through a **Sling Servlet** to the specific **OSGi Service** implementation, accounting for `@Reference` bindings and `sling:resourceType` resolutions.

## 2. OSGi Service Dynamics & `bnd` Integration
Modern AEM (Cloud Service) relies heavily on the `bnd-maven-plugin` for metadata generation. Standard static analysis often fails here because it doesn't account for:
*   **Inherited References:** Services inheriting `@Reference` from parent classes or interfaces.
*   **SCR Metadata:** The `OSGI-INF/*.xml` descriptors generated by `bnd` that the OSGi Service Component Runtime (SCR) actually uses.
*   **Capability Resolution:** `Require-Capability` and `Provide-Capability` headers in the `MANIFEST.MF`.

**The Dede-Java Value:** It mimics the **OSGi Resolver** logic. By analyzing the generated SCR metadata and Bundle Manifests, it identifies "Unsatisfied References" or "Zombified Services" (active but unreachable) *before* deployment to AEM Cloud.

## 3. Dispatcher-to-Bundle Reachability
Security auditing in AEM is notoriously difficult because Dispatcher rules are decoupled from the Java Servlet registry.
*   **The Pain:** An "Open" Dispatcher rule might inadvertently expose a sensitive OSGi Servlet that was intended for internal use only.
*   **The Dede-Java Value:** It performs **Cross-Layer Reachability Analysis**. It maps Dispatcher `allow` rules directly to the implementing Java classes. If a change in Java code (e.g., changing a `path` in a `@SlingServletPaths`) breaks a Dispatcher contract, `dede-java` flags the "Security Gap" or "Broken Path" immediately.

## 4. Content-to-Code "Zombie" Detection
AEM projects often suffer from "Model Bloat"—hundreds of Sling Models for components that have long been deleted from the JCR.
*   **The Pain:** Developers continue to maintain and test code that is never instantiated in production.
*   **The Dede-Java Value:** By scanning the **JCR Content Hierarchy** alongside the Java classpath, it identifies **Orphaned Models**. It flags Java classes that have no corresponding `sling:resourceType` usage in the repository, enabling "Surgical Deletions" of dead code.

## 5. OSGi Configuration Policy & Environment Mapping
A common "silent failure" in AEM Cloud is a service that is syntactically correct but functionally dead due to missing configurations.
*   **The Pain:** A component with `configurationPolicy = ConfigurationPolicy.REQUIRE` will not start if its OSGi config is missing from the specific environment folder (e.g., `config.prod`).
*   **The Dede-Java Value:** It cross-references JCR-based OSGi configurations (`.cfg.json`) with Java component metadata. It flags **"Configuration Gaps"** where a service is deployed but will remain in a `SATISFIED` (but not `ACTIVE`) state due to missing runtime properties.

## 6. Sling Model Adaptation & Null-Pointer Prevention
Sling Models often fail silently (returning `null`) when the adaptable type is mismatched.
*   **The Pain:** A model defined as `adaptables = SlingHttpServletRequest.class` is accidentally adapted from a `Resource` in a HTL script or Java utility.
*   **The Dede-Java Value:** It tracks the **Adaptation Context**. By analyzing HTL `data-sly-use` and Java `adaptTo()` calls, it detects mismatched adaptations where the source object doesn't satisfy the `@Model` requirements.

## 7. Service Ranking & Target Filter Resolution
In complex systems with multiple implementations of a single interface (e.g., custom `Rewriter` or `WorkflowProcess`), OSGi resolution is non-trivial.
*   **The Pain:** Relying on `service.ranking` or `@Reference(target = "...")` filters makes it hard to see the actual wiring without the Felix Console.
*   **The Dede-Java Value:** It simulates the **OSGi Service Registry**. It resolves LDAP target filters and ranking priorities to show the architect the **Actual Provider** of a service, preventing "Shadowing" bugs where a legacy service unexpectedly takes precedence over a new implementation.

## 8. Continuous Architectural Renovation (The "Renovate" Loop)
To a modern DevOps team, `dede-java` is the "Architectural Manager" that complements tools like **Renovate Bot**.
*   **The Synergy:** While Renovate automates version updates in `pom.xml`, `dede-java` automates the validation of those updates against the **OSGi Runtime Reality**.
*   **Compatibility Guardrails:** When Renovate proposes a major SDK update, `dede-java` performs a bytecode-level impact analysis. It identifies exactly which custom OSGi services will fail to resolve due to breaking API changes, moving the "fail-fast" point from the AEM Cloud deployment to the Pull Request.
*   **Automated Cleanup:** Just as Renovate removes unused dependencies, `dede-java` identifies "Architectural Debt" (Zombie Models and Orphaned Servlets) that are no longer referenced by the JCR. This enables a workflow of **Continuous Cleanup**, ensuring the codebase stays lean as the AEM content structure evolves.

## 9. Security Reachability & Risk Prioritization (The "Dependabot" Filter)
In a modern security-first environment, `dede-java` acts as the architectural lens for tools like **Dependabot**.
*   **Beyond the CVE:** Dependabot identifies vulnerable libraries (CVEs). `dede-java` determines **Exploitability Path**. It traces the path from a public **Dispatcher Filter** to the specific **Sling Servlet** or **Model** using the vulnerable library.
*   **Risk-Based Patching:** If a critical CVE is found in a library used only by a background OSGi task (not reachable via HTTP), `dede-java` lowers its priority. If the library is used by a public `/bin/submit` servlet, it escalates the priority to "Immediate."
*   **Compliance Guardrails:** Just as Dependabot flags outdated versions, `dede-java` flags "Forbidden" API usage (e.g., legacy `com.day.cq` packages or internal AEM APIs) that will cause deployment failures in AEM as a Cloud Service.

## 10. AEM Cloud Service "Forbidden" & Deprecated Patterns
`dede-java` acts as a local "Pre-flight Scanner" for AEM Cloud Manager. It identifies architectural patterns that are explicitly deprecated or removed in AEM as a Cloud Service.

### A. Forbidden Java API Usage (Cloud Manager Fails)
Instead of waiting for a "Build Failure" in Cloud Manager, `dede-java` identifies these legacy packages in the bundle classpath:
*   **Workflow:** `com.day.cq.workflow.*` (Must use `com.adobe.granite.workflow.*`).
*   **Replication:** `com.day.cq.replication.*` (Must use `org.apache.sling.distribution.*`).
*   **Search:** `com.day.cq.search.*` (Direct use of GQL/Legacy Search is discouraged; use QueryBuilder or Oak Index).
*   **Internal APIs:** Any usage of `com.adobe.granite.*.impl` or `com.day.cq.*.impl` (These are "Internal" and hidden by the Cloud Service Java Classloader).

### B. Deprecated JCR Paths & Content Structures
AEM Cloud Service enforces a strict separation of "Immutable" (`/apps`, `/libs`) and "Mutable" (`/content`, `/conf`) content. `dede-java` flags:
*   **Legacy Workflow Models:** `/etc/workflow/models` (Must move to `/var/workflow/models`).
*   **Legacy Designs:** `/etc/designs` (Must move to `/apps/settings/wcm/designs`).
*   **Classic ClientLibs:** `/etc/clientlibs` (Must move to `/apps` or `/libs`).
*   **Direct Asset Manipulations:** Accessing `/content/dam/.../jcr:content/renditions` directly, bypassing the **Asset Microservices** abstraction.

### C. Deployment & Configuration Risk
*   **Run Mode Ambiguity:** Use of generic `config.author` or `config.publish` folders without environment-specific suffixes (`.dev`, `.stage`, `.prod`) which can lead to "Configuration Drift."
*   **Service User Leakage:** Identification of code that still attempts to use `session.loginAdministrative()` or `resourceResolverFactory.getAdministrativeResourceResolver()` (Both are strictly blocked in AEMaaCS).

## 11. Testing & Verification (The "Quality" Loop)
To maintain its "Expert-Grade" status, `dede-java` provides built-in verification mechanisms for both its OSGi and Standalone distributions.

### A. OSGi Bundle Validation
Verify that the generated JAR is a valid OSGi bundle by inspecting the `MANIFEST.MF` headers:
```bash
unzip -p target/dede-java-*.jar META-INF/MANIFEST.MF | grep -E "Bundle-SymbolicName|Export-Package|Import-Package|Service-Component"
```
*   **Symbolic Name:** Must be `com.dede.dede-java`.
*   **Export-Package:** Must include `com.dede.osgi`, `com.dede.core.model`, `com.dede.core`, and `com.dede.analysis`.
*   **Service-Component:** Must reference `OSGI-INF/com.dede.osgi.DedeOsgiScanner.xml`.

### B. SCR Metadata Verification
Ensure the Declarative Services (SCR) metadata is correctly generated for AEM deployment:
```bash
unzip -p target/dede-java-*.jar OSGI-INF/com.dede.osgi.DedeOsgiScanner.xml
```
*   The component must `provide` the `DedeOsgiScanner` interface and `reference` the `ProjectScanner` interface.

### C. Spring Boot CLI Verification
Verify that the executable JAR can run in a non-interactive/CI environment:
```bash
java -jar target/dede-java-*-exec.jar . --profiles aem --dot target/output.dot
```
*   This command performs a full scan of the current directory, generates an architectural graph in DOT format, and outputs AI-driven refactoring suggestions.

### D. Docker Image Build
Verify the multi-stage `Dockerfile` by building the image locally:
```bash
docker build -t dede-java:latest .
```
*   **Stage 1:** Uses Maven 3.9.6 to build the bundle and executable JAR.
*   **Stage 2:** Uses a lightweight JRE 21 image for the final runtime, ensuring a small attack surface and efficient container startup.
